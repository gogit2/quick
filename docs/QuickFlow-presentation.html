The assignment

What had to be built, and how

The product (from the PRD)

  • Six pages: Dashboard, Tasks, Habits, Learning Resources, Todo Plans, Settings
  • Tasks with search, filters and overdue; recurring habits with streaks; learning cards with milestones and notes
  • Plans built from existing items, with a live rest-time countdown, a start notice and progress
  • A dashboard that always matches the data

The brief

  • Use reusable Claude loops: backend-dev and frontend-dev, each with Loop-instructions, task, progress, state, outputs
  • Backend tested with curl and Swagger; frontend tested with the Playwright MCP
  • Loops usable on a whole PRD, a single user story, directly or through an orchestrator
  • Deliverables: repo, Excel of prompts and sessions, mermaid diagrams, a design document
Stack: Java 17 · Spring Boot 3.5 · Flyway · H2 · springdoc  |  Angular 19 · Material · Node 18  |  Playwright MCP 0.0.40 · Prism mock · Haiku 5.5 (build) · Opus 5.5 (verify) · Sonnet 5.5 (plan, retry)
The approach

Plan once with Spec Kit, then let bash run the milestones

Planning is interactive

Constitution, one spec for the whole PRD, clarification questions answered by me, plan, contract, tasks, acceptance, analysis, then an approval gate.

Building is unattended

Each milestone: backend and frontend build in parallel, a verifier checks the real stack, the runner commits and tags, the next milestone starts.

Bash owns control flow

State, trials, budget, servers and git live in scripts. A Claude session does one iteration of work and exits. All memory is in files.

Why parallel works

The contract is the single source of truth

Designed first

Every operation has an x-milestone and examples. Loops cannot edit it; problems go to contract-issues.md.

Checked mechanically

The Swagger exported from the running backend is diffed against the contract: operations, parameters, response codes, schemas, enums.

Mocked for the frontend

Prism serves the same file, so the UI is built and tested before the backend exists.

The loops

Three roles, one protocol

backend-dev Haiku 5.5

  • Spring Boot to the contract, Flyway migrations
  • JUnit for every business rule, injected Clock
  • A curl suite per milestone
  • Exports Swagger from the code

frontend-dev Haiku 5.5

  • Angular + Material against a Prism mock
  • Playwright MCP scenario per feature, with screenshots
  • data-testid on everything a test touches

verify Opus 5.5

  • Runs the real full stack from a fresh database
  • Review, Swagger diff, JUnit, curl, Playwright
  • Fixes small issues itself, otherwise rejects with FIX tasks

Every loop folder has the same files

Loop-instructions.md · task.md · progress.md (runner table: start/end, tokens, cost, session ids + the agent's action log) · state/ · outputs/ (one markdown per milestone with ticked tasks, plus curl/, e2e/, evidence/)

Reusable on purpose: run-loop.sh --role R --ref US-TSK-02, pipeline.sh --story "..." or --input other-PRD.md plan a new spec and continue the milestone numbering.

Inside a loop

One iteration is one fresh session

The agent's claim of "built" is never trusted on its own: the runner re-runs the build, the curl suite and the Swagger diff (backend) or ng build and the Playwright result file (frontend).

The barrier

Backend and frontend in parallel, then verify, then the next milestone

Waiting costs no tokens (plain bash wait). A REJECT adds FIX tasks to the affected role's milestone file and counts one trial.

The verifier

Real stack, real data, one round

Small fix rule

At most 3 files, about 30 lines, no design or contract change. Logged in the report; the affected checks are re-run. Bigger problems become FIX tasks.

What it checks on top of the loops

The milestone's scenarios with real state, every [smoke] scenario of earlier milestones, empty states on a fresh database and error states with the backend stopped.

Guards

What keeps an unattended run safe

Trials and upgrade

Failed self-check, failed gate, no progress or a verifier REJECT each cost a trial. After 3, one retry on Sonnet with a fresh budget, then blocked for the user.

Budget

$15 per milestone ($25 for the two largest) checked between sessions, plus a hard --max-budget-usd per session. Not one milestone came close.

Permissions

Each role has its own allowlist. Dev loops cannot commit, tag, push or edit the contract; only the runner commits.

Deterministic gates

The runner re-checks every "built" claim: build, tests, curl, Swagger diff, Playwright result file.

Servers

Started and stopped only through PID-file scripts with health waits and trap cleanup.

Resumable

State is in milestones.json. The pipeline resumes after an interruption, a suspend or a blocked milestone.

What the verifier caught

Real bugs that the builders' own checks missed

M02

Server-side validation errors were not shown on the form fields.

M04

After a successful add, the form kept its submitted state and showed validation errors on empty fields.

M06

A failed habit/plan toggle left the checkbox visually checked although the data said not done.

M07

Material buttons had no visible keyboard focus ring (the library removes the outline).

M08

Shadow tokens were invalid CSS (light-dark() accepts colours only, not a whole box-shadow).

M09

Snackbar styling used token names Angular Material 19.2 ignores; switched to the ones it reads.

M10

First expand of a learning card did not animate; a 0% progress bar looked full in the light theme.

M11

Material's own 400 ms rule overrode the sidenav transition; a date was glued to a title on the dashboard.

Each one was fixed by the verifier within its small-fix limit (3 files, about 30 lines) and re-tested. Without a separate Opus pass on the real stack, these would have shipped.

Honesty slide

What went wrong, and what each thing taught

M03: a lost claim

The frontend loop reported 'built' but the runner's own gate failed. One trial used, fixed next iteration. Why the runner never trusts the claim.

Pipeline stopped after M02

A bug in my runner: child processes read the milestone list from stdin and ate it. Fixed by reading the list into an array first.

The laptop slept (M06)

Two sessions froze for 3 h 42 min across a suspend. Killed, restarted without counting a trial, and a suspend watchdog plus systemd-inhibit were added.

M11 blocked, by design

3 trials plus the Sonnet retry were used on one item: a 3.4 kB overshoot of a 600 kB raw bundle budget. A decision for the user, not a skill gap: budget raised to 650 kB (transfer size was 150 kB vs 500 kB goal).

Mock limits

A stateless Prism mock cannot show empty states or errors, so those scenarios are tagged real-stack-only and run by the verifier. Four old scenarios could not pass the mock at all; the user decided to ignore them (D-26).

A spreadsheet re-saved the log

A BOM and Windows line endings broke the Excel export. Cleaned, and the reader now tolerates it.

Lessons

What I would keep, and what is still open

Keep

  • Contract first is what makes the parallel run safe
  • Cheap builders + one strong verifier: Haiku's bugs were caught by Opus on the real system
  • Never trust a "done" claim: re-check it with the runner
  • Blocked is a feature: a stuck milestone stops and asks, it does not guess
  • Planning interactively, building unattended

Open items

  • Four old scenarios are ignored for the M11 regression (decision D-26); nobody re-checks them against the restyled UI
  • The empty-state add button is not filled as the task asked (a verifier backlog note)
  • The active nav item is a very bright cyan in the light theme: a visible rough edge
  • Plan editing, drag-and-drop priority, charts and tags are out of scope (backlog)
  • The design document is mine to write; this deck is not that document
